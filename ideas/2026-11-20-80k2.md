Coordinator waits in T3: lost wakes, and the fixes (research from braid 0040)

The coordinator of braid 0040 kept going quiet while it waited. A research thread found why on 2026-11-20, using T3's provider log, the Claude Code transcript and the thread activity.

What happens:
1. A background-command wake kills the session. This is a T3 bug. When the last background Bash task ends, T3 releases the Claude session (`ProviderSessionManager.releaseIfStillIdle`, `idle_timeout`, then `query.close`). That happens about 20 ms after Claude Code has started the wake turn for the task's notification, and before T3 registers that turn (`claude-wake-turn-detected`). The turn's tool calls still run as orphans, but their results are lost: `braid start 0040/D`, `0040/E` and `0040/F` all ran unseen, and the thread sat settled until the user wrote. On the next resume Claude Code shows "session ended before this call's result was recorded". The process tree isn't killed: an orphaned `braid start` pushed its branch 9 s after the resumed coordinator had looked for it.
   - Close timings (task done, then query.close): 18:23:11.929 → .945; 19:26:26.333 → .350; 20:13:07.964 → .985; 00:04:16.056 → .076; 00:34:59.451 → .471.
   - 1 of 6 wakes survived (00:12:16, while a worker was still running).
   - Evidence: `~/.t3/userdata/logs/provider/events.72214140-*.log`.
2. `t3_thread_wait` has no time limit, but it ends within 2–10 ms of any message reaching the thread: the user's, a worker's or a reviewer's. That steer also cancels tool calls running alongside the wait, and the cancelled call reads "The user doesn't want to take this action right now. STOP", which the coordinator mistook for the user declining.
3. Reliable wakes in T3: a worker's `t3_thread_send` into the coordinator; `watch_pull_request`, though it is queued until the session is free and can arrive stale; and a `delegate_task` result. A background Bash command with `t3_background_wait` is not reliable.

Fixes:
- **Report the bug to T3** (the user files it): don't release the session while a task notification is buffered or a wake turn is starting, and kill the process tree on close.
- **Braid skill** (`references/autonomy.md` step 4; SKILL.md "Say waiting only when"): wait for braid-branch CI in the foreground, under 10 minutes per call and repeated, and drop the background-command wake.
- **`braid wait` (D70):** a bounded foreground mode with a distinct "still running, call again" exit code, and clear `--timeout` units.
- **`braid start`:** idempotent. When the branch and worktree already exist at the expected base, say "already started" and exit 0, so a retry after a lost result is safe.
- **Coordinator habits:** after any wake or resume, re-check the state first (`braid next`, branches, worker threads). After "session ended", wait about a minute before retrying. Run nothing in parallel with `t3_thread_wait`. Treat a "STOP" result during a wait as an incoming message, not the user. Prefer the wakes T3 owns over long blocking waits.
