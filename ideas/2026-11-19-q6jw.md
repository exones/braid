Evidence folder per item, with a manifest

An item may keep an evidence/ folder: screenshots, data extracts, test results. Its README says what each file proves, the commit it was captured from, how it was captured, and the command to reproduce it; before/after pairs are named consistently (e.g. before|after-<n>-<screen>-<theme>-<width>.png). report.md links each claim to its file and adds a "Not proven" line that says how far the claims go. A fix records its test failing on the base and passing after (command, base commit, counts), not only a sentence. Images are kept small (a size limit, 256-colour PNGs). This extends 2026-11-18-bvcs (workers say how they verified) with where the proof lives.

Today: validation is prose to trust. 0025's report says "With openCounts temporarily calling readInbox(root, { fetch: true }) the new test fails (5 leftovers instead of 4); reverted", with no command or output kept, so a reviewer can't rerun it without working out the steps. For UI items, 0020/C kept the approved mockups, but nothing compares the built board to them; for 0033 (board says why an action is forbidden) the proof would be one screenshot per forbidden state, which now lives at best in the worker's chat.

Example:
  braids/0033-.../evidence/
    README.md          captured at a1b2c3 with <command>; shows each disabled button's reason; compare with mockups/x.png
    after-1-merge-forbidden-light-1440.png
    fails-before.txt   command, base commit, "2 failed / 48"

Utility: high for UI items and for fixes (the fails-before record); low for ordinary CLI tasks, where CI already serves as the evidence (D28). Keep it optional and small.

Why: Sergei's initiatives keep proof this way (everix4 initiatives/everix/015-ifr-eba-coverage/proof/*/README.md, 022-functional-gap-assessment/evidence/*/test-results.json). His version also shows what to avoid: seven different folder names for the same thing, ~90 MB of PNGs in plain git, and proof pointing to local disks outside the repo.
