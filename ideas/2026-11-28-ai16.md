Revisit a rebuildable SQLite index when the braid record outgrows files. 2026-11-28, the user asked whether .braid state and the record branches (requests, lifecycle) should move to SQLite. Today: agento .braid is 5 small JSON files (20 KB), braid-requests has 135 small files; counters are derived on each read, not stored. Pain so far is concurrency (parallel braid new took one number, idea l2s7; lock tests; git processes per record write, 0077/H) and slow git/T3 reads (0077), not volume. The git branch stays the shared truth on purpose (user, 2026-11-22, Q1 "A"): every agent, worktree, phone and machine sees it through origin. Triggers to revisit: (1) a project reaches thousands of records and reads stay slow even with the board in-memory copy; (2) the board needs real queries across projects (history, statistics) that would read every file; (3) several machines write the same record at the same moment. Likely shape then: the board keeps a local SQLite index rebuilt from git at any time, a cache, never a second source of truth.
