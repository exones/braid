# BRAID-003/F epic workspaces and assignments

The approved epic-branch, workspace, and assignment rules are now in the maintained authorities, and a top-level item thread is the normal way to wait on its own pull request. Hosted proof for this head is checked after push and is reported to the coordinator. It is not written back into this blob. Independent review and the human merge into the epic are still separate.

## What changed

- New epics start on a pinned integration branch taken from verified main. Item branches start from the accepted epic tip, and their pull requests target the epic. One final epic pull request targets main. Item Done is the human merge into that epic. Epic completion and release stay separate. History already on main is left as it is.
- The default checkout split is one coordinator epic worktree and one active item worktree, with one writer in a checkout. The host creates and binds the named branch. A missing, detached, or wrong-branch checkout stops the affected writes. Startup HEAD must match the epic tip supplied at launch. Later commits stay on that branch. Retirement is limited to a stopped, clean, owned workspace after its evidence is kept. Adopting the policy does not retire existing workspaces.
- New packets are committed at `assignments/<ID>.md` before the item checkout exists. Review packets may use `assignments/reviews/<parent>/`. Reports, checkpoints, and historical `reports/<ID>-assignment.md` files stay where they are.
- A top-level item thread links and watches its own pull request, ends the turn, and one watch wake drives verification and one coordinator result. The coordinator dedupes by head. The worker prompt stays short and step-explicit. The parent relay remains only for an explicitly selected delegated child.

## Why

BRAID-003 had been mixing item bases, checkout ownership, and assignment locations, and the parent relay was waking the coordinator for every CI event. The user-approved policy and the G watch-wake evidence give one delivery shape for the remaining work and for later epics. Without the short prompt and the dedupe rule, a long resume prompt can restart inside one run and send the same head again.
