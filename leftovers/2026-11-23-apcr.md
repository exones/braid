The steering thread: an LLM retypes ids and settles before the replies

Field run, 2026-11-23 23:31 (steering thread mcp:ea3bcdca-37c2-…, codex / gpt-6-luna, everix project, Claude_Everix Weekly 95%):
- It sent the pause to all 17 targets, and every agent paused. But the pause text named the steering thread as `mcp:ea3bcdca-37cc2-…` (an extra "c": the model retyped its own id), so no reply could reach it. Agents worked around it, relaying through coordinators and the PM.
- It reported "Steering: Claude_Everix paused 0/17 … no answer: <all>" and settled about 40 s after sending, instead of collecting replies for up to 10 minutes. The replies then arrived as new turns, which it answered with empty messages and never counted. So the board's record says 22 agents didn't answer, while almost all did.
- The user wrote "I used a reset, unpause all" in the thread. It sent a generic "Claude_Everix Weekly has resumed" to all 17, but the board's pause records stayed (the PM cleared three by hand), and the board has no early resume after a reset.

Fix in the spirit of "reliable calls": the board sends the pause and resume messages itself with `t3 thread send`, as it already does for the resume, with ids filled in by code and no LLM retyping them. It counts the replies from the threads (or from replies to the board's own message). It offers one action, "resume now", for a reset (`braid resume --limit` for every board pause plus the resume sends). If a steering thread stays, it only relays text the board wrote, verbatim.
