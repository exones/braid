Concurrent changes to the same inbox entry: the later write wins
Sweep commands rewrite an entry's front matter (status, passed, into, why). When two clones change the same entry, write() in src/inbox/branch.ts re-runs the change on the fetched tip, so the later write's version wins without notice. Worse, an offline commit that changed an existing entry is replayed by rebase() / commitOn() as whole files on top of the remote tip, overwriting a newer remote version of that entry (for example a pass replayed over someone's take). Entries are never lost, but a status can silently go back. Matters once sweeps run from more than one clone; replaying a change of an existing file should rebuild it from the newer tip or refuse.
