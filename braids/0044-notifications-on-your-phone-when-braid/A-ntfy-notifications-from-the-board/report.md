The running `braid board` now sends ntfy pushes to the phone, set up once per machine with `braid notify`.

- `braid notify setup [--topic <t>] [--server <url>] [--new-topic]`, `test`, `off`, and the bare state (`src/commands/notify.ts`, `src/notify/config.ts`). Settings in `~/.braid/notify.json` (`server`, `topic`, `enabled`); the topic is `braid-` + 24 characters from `crypto.randomInt`; the server must be `https://`; the token only from `BRAID_NTFY_TOKEN` (Bearer), never stored or printed. The full topic shows only in `setup`'s output; everywhere else its first 10 characters.
- The pushes (`src/notify/message.ts`): one per item in Needs You or To Review, per strand on a braid card with strands (plus the braid's own need when it is the card's top need), and one per Done braid card. Title `<repo> <id>: <lane>`, body title + need line, a tag per reason, priority high for Needs You, click the thread's `t3code://` app link. Nothing else from the repository.
- The notifier (`src/notify/notifier.ts`): after each snapshot with GitHub and T3 ok, compares with `.braid/notified.json` of the main checkout (temp file + rename, re-read before each write), sends new keys without awaiting, stores a key only after success, drops keys whose need left, records Done braids silently on the first run (no or unreadable file). Failures print once per outage, name only the server, and retry at the next refresh; a send that hangs times out (10 s in the sender, 11 s guard in the notifier) and an in-flight key is never sent twice.
- `Need` gained `since` (when the request was made or the alarm began), which the key uses.
- `src/commands/board.ts`: `Sources.notify`, called in a try/catch after each ok snapshot; only `runBoard` adds it, so board tests never read the real `~/.braid`. `runBoard` prints the notifications line; the demo says none.
- Sending uses ntfy JSON publishing (`POST <server>` with `topic` in the body) rather than headers, because HTTP headers can't carry non-ASCII titles.
- Docs: `docs/cli.md`, `docs/board.md` (Notifications section; Refresh now mentions `notified.json`), `docs/decisions.md` D70 and its log line.

Validation: `test/notify.test.ts` (16 tests: config and topic, the CLI in a temporary HOME/USERPROFILE, message fields, strand needs, dedupe across a simulated restart, leave and return, Done at first run vs later, corrupt file, sources down and off, failed send retried, hanging send, the real sender against a fake `fetch`, the board with a throwing notifier). `npm run verify` passes (353 tests). Not tried against a real ntfy server or phone.

Open: a braid's own request that is outranked on its card by a more urgent strand need is pushed only once it becomes the card's top need. A machine without T3 (T3 unreadable) never sends, as the brief requires.

Decisions: setup keeps an existing topic unless `--topic` or `--new-topic` is given, so turning pushes back on after `off` keeps the phone's subscription; D70 numbered after 0040's D68; JSON publishing for UTF-8 titles; the click link is T3's `t3code://` app link because T3's own link is a 127.0.0.1 page the phone can't open; a braid's own need clicks to its coordinator thread.
For later items: `Need.since` (ISO) is new in the board data. 0044/B's braid-level `stalled` will be pushed with no change here, provided its need sets `since` to the alarm's start (otherwise the key falls back to `-` and a returning stall still resends after the need leaves).

Review whether that content and the setup flow are acceptable before merge.
