# Research: review practices for the braid reviewer

Read on 2026-11-17. "How read" says what I actually had in front of me:

- **full**: the raw file or the paper's text, downloaded and read.
- **page**: the web page, read through the fetch tool, which returns an extract of the page, not every word.
- **abstract**: only the abstract or landing page.

Nothing here is taken from search-result snippets. What I looked for and could not read is at the end.

## What the sources agree on

1. **Most wrong findings come from not reading around the diff.** In SWR-Bench, 48% of sampled false positives were "lack of contextual understanding". Bacchelli and Bird found understanding the change is the reviewer's main difficulty, and that finding defects needs the most of it. OpenAI's review skill reads "enough surrounding code to understand each changed path" and checks "tests and call sites" before reporting. Google: look at the whole file and the system, not the few lines shown.
2. **A finding is a concrete case, not a feeling.** OpenAI's rubric wants "the scenarios, environments, or inputs that are necessary for the bug to arise", and a claim that other code breaks must "identify the other parts of the code that are provably affected". Anthropic's security review asks for an exploit scenario per finding.
3. **A self-reported confidence number is a weak gate.** Greptile had the model score its own comments 1 to 10 and found the judgment "nearly random". Anthropic's plugins don't trust the first pass either: a separate step re-checks each finding against the code.
4. **Pushing for silence loses real bugs.** CR-Bench: best recall is about 33%, and every setup trades recall against noise. The Copilot study found it missed SQL injection and XSS while commenting on style. Cursor's agentic Bugbot was "too cautious" and had to be told to lean toward flagging. Agent Patterns: a strict floor hides cross-file bugs, and "silence looks the same as a clean bill of health". Anthropic's own docs: no findings "doesn't mean your code is error-free".
5. **Tests need reviewing as tests.** Google: "Will the tests actually fail when the code is broken?" Anthropic's test analyzer looks for untested error paths, missing negative cases and tests tied to implementation.
6. **Errors that vanish.** Anthropic's silent-failure agent: catch blocks that log and continue, defaults returned on failure, fallbacks that mask the problem.
7. **What to leave out.** Both vendors: preexisting problems, style a linter catches, intentional changes; one comment per distinct problem (GitHub groups repeats).

For braid this means: its reviewer posts one comment and already sorts by a blocking bar, so it doesn't have the bot noise problem a 90% floor solves. The gate should be evidence (the case), and blocking-class suspicions must not be filtered out.

### Studies

| Source | How read | What it says | Adopted? |
|---|---|---|---|
| Bacchelli and Bird, "Expectations, outcomes, and challenges of modern code review", ICSE 2013. [PDF](https://web.eecs.umich.edu/~weimerw/2018-481/readings/codereview.pdf) | full (sections V and VI; the rest skimmed) | Of 570 review comments at Microsoft, 14% were about defects, mostly "uncomplicated logical errors"; understanding the change is the main difficulty, and finding defects needs the most understanding; reviewers who know the files find "subtle defects" instead of surface points. | Adopted: read around the diff before judging. |
| Czerwonka, Greiler and Tilford, "Code reviews do not find bugs", ICSE 2015. [PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2015/05/PID3556473.pdf) | full (a three-page paper) | About 15% of comments point at a possible defect; usefulness rises with the reviewer's prior exposure to the code (33% useful on first contact, 67% by the third) and falls for reviews of 20 or more files. | Supports reading around the diff. Size limit not adopted: the brief's expected size and the worker's "twice the size" rule cover it. |
| Sadowski et al., "Modern code review: a case study at Google", ICSE-SEIP 2018. [PDF](https://sback.it/publications/icse2018seip.pdf) | full (skimmed; sections 5 and 6 read) | Small changes (median 24 lines), usually one reviewer; breakdowns come from missing context about why the change was made. | Not adopted: braid already gives the reviewer the brief. |
| Zeng et al., SWR-Bench, arXiv 2509.01494. [HTML](https://arxiv.org/html/2509.01494v2) | page (first 100,000 of 130,000 characters) | 1,000 real PRs: best tool at 19% F1, precision under 10% for four of the tools; logic errors are found best; of 100 sampled false positives, 48% lacked context, 17% over-reacted to a modification, 16% were vague and unactionable. Merging several independent reviews raised F1 by up to 44%. | Adopted: read around the diff; a finding must be a concrete case. Multiple reviews not adopted (cost; the coordinator's choice). |
| CR-Bench, arXiv 2603.11078. [HTML](https://arxiv.org/html/2603.11078v1) | page | On 174 verified cases, recall 27% to 33% and precision under 6%; pushing the agent to find more ("when in doubt, keep the issue") raised recall and cut signal-to-noise from 5.1 to 1.9. The authors prefer the thorough setup "for security-critical audits or high-risk refactoring". | Adopted as the shape of the rule: keep likely blocking-class problems even unconfirmed; hold everything else to the concrete-case standard. |
| Amro and Alalfi, "GitHub's Copilot Code Review: can AI spot security flaws before you commit?", arXiv 2509.13650. [abstract](https://arxiv.org/abs/2509.13650) | abstract | Copilot review "frequently fails to detect critical vulnerabilities such as SQL injection, cross-site scripting (XSS), and insecure deserialization" and mostly comments on style and typos. | Supports the same rule. Abstract only, so no weight on details. |
| Mäntylä and Lassenius, "What types of defects are really discovered in code reviews?", IEEE TSE 2009. [author's page](https://mmantyla.github.io/wiki/What+Types+of+Defects+Are+Really+Discovered+in+Code+Reviews%253F.html) | abstract | 75% of defects found in review don't affect visible behaviour; they are about how easy the code is to change. | Not adopted: background. It explains why a blocking bar is needed, which braid has. |
| Petrović and Ivanković, "State of mutation testing at Google", ICSE-SEIP 2018. [abstract](https://research.google/pubs/state-of-mutation-testing-at-google/) | abstract | Google shows surviving mutants (small injected faults the tests don't catch) to reviewers during code review. | Supports "would this test fail on the old code?" as the manual version. Tooling not adopted. |

## What changed in the skill because of this

| Line in `braid-reviewer/SKILL.md` | From |
|---|---|
| Read around the diff: changed functions whole, their callers, docs and decisions made stale | SWR-Bench, Bacchelli and Bird, Codex review-agent, Google |
| Failure paths, now with errors swallowed or hidden behind a default | Google (edge cases, concurrency), Anthropic silent-failure-hunter |
| Test the tests | Google, Anthropic pr-test-analyzer, mutation testing |
| A code finding names the input or state and the wrong result | Codex rubric, Anthropic security-review |
| A likely blocking-class problem stays Blocking unless a run disproves it; "unverified" only for weaker suspicions; no percentage | CR-Bench, Copilot study, Cursor, Agent Patterns' caveats, Greptile; the review of this PR |
| Say what you could not check | Anthropic docs, Codex review-agent, Google, Agent Patterns |
| Skip style and preexisting problems; a repeated problem once | Codex rubric, Anthropic code-review, GitHub |
